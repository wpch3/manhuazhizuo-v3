# 仓库体积规范（本项目硬性要求）

## 为什么有这个文件

上一轮生成的原画与成品 PNG 每张 3–5 MB，11 页正文就接近 50 MB；
原画另有一份 25 MB。这样每更新一话，仓库就会膨胀一倍，
很快会撞到快照上限，导致 Git、读写和 gh 都不可用（v1 项目曾因此整轮无法交付）。

## 三层分级

| 层级 | 位置 | 格式 | 上限 | 是否入 Git |
|---|---|---|---|---|
| **归档母版** | `art/lv1/master/` | PNG（1440×1920） | 单张 ≤ 6 MB | **不入 Git**（.gitignore） |
| **原画** | `art/lv1/*.png` | WebP 质量 92 | 单张 ≤ 600 KB | 入 Git |
| **成品** | `deliverables/lv1/*.png` | WebP 质量 95 | 单张 ≤ 900 KB | 入 Git |
| **试读 PDF** | `deliverables/*.pdf` | JPEG 质量 95 内嵌 | ≤ 15 MB | 入 Git |

## 铁律

1. **不要提交 3 MB 以上的 PNG。** 需要无损时放 `art/lv1/master/`（已 gitignore），
   需要进仓库的一律转 WebP。
2. **成品不重复存原图。** 成品页与试读 PDF 由 `scripts/build_lv1.py` 生成，
   不做第二份拷贝。
3. **字体是必要资产。** Noto Sans CJK 两个 OTF 共 32 MB，属例外，
   允许入 Git；不得因为体积删掉它们（否则排版无法复现）。
4. **每话结束检查体积**：`du -sh art deliverables`，`git count-objects -vH`。
5. **不许用 `.gitignore` 藏交付物。** 被忽略的只能是母版或临时文件，
   用户能看到的成品必须在 Git 里。

## 一键压缩

```bash
python3 scripts/compress_assets.py            # 转换全部原画与成品
python3 scripts/build_lv1.py                  # 重新出 PDF
```
